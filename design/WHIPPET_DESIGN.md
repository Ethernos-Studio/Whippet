# Whippet 初步设计文档

> 版本：v0.6（实现语言与构建系统已定，配 M0 脚手架）
> 日期：2026-11-08
> 状态：设计定型，M0 可开工（见 WHIPPET_M0_SCAFFOLD.md）

---

## 1. 项目概述

Whippet（小灵缇）是 Ethernos Studio 的**独立编译器后端项目**：接收前端产出的 Whippet IR，负责中端优化与机器代码生成。名字取"为速度育种、体重极轻的猎犬"之意，对应编译器后端的两个核心指标——**编译快**与**内存轻**。

命名验证：2026-11-08 两轮搜索（开发工具方向、GitHub/npm/crate 方向）零冲突。

定位：**Whippet 不依附于任何前端，也不替前端做适配**。ETCC 是首个预期借用方——它当前使用 LLVM 作为后端；将来切换时，由 ETCC 自己负责把它的 IR 适配成 Whippet IR（或者改完前端后直接 emit Whippet IR）。从任何语言（包括 LLVM IR）到 Whippet IR 的翻译层都属于前端，不属于 Whippet。Cavvy 远期同理。

## 2. 设计目标

| 目标 | 量化指标（推导见 §9） |
| --- | --- |
| 编译快 | ≥ 20k 行/秒（单线程，-O1 档）；5k 行单文件 ≤ 0.25 s |
| 内存轻 | 峰值内存 ≤ 16 × 源文件字节数 |
| 代码质量 | 简单基准上不超过 gcc -O1 的 20%（不追 -O2） |
| 可自举 | 远期支持借用方（ETCC）自编译（Windows 目标） |

### 非目标

- 不做跨平台框架层的一等抽象：第一平台就是 Windows x64 COFF + MSVC ABI，SysV / ARM64 是后续移植而非设计中心
- 不做激进优化：不抄 LLVM 那套（循环展开/向量化自动调优/SROA 全家桶），-O1 目标是"O1 质量、O0 成本"
- 不做前端适配：从源语言或 LLVM IR 到 Whippet IR 的一切 lowering、mem2reg、语义裁决（如 poison）都是前端职责
- 不为 C 全集一次性开工：v1.0 覆盖 §10 列出的 C 子集

## 3. 接入契约：Whippet IR

前后端的边界就是 Whippet IR：前端产出它，Whippet 消费它。后端唯一接受的输入是 Whippet IR 的文本形式（调试/跨进程）与内存形式（库 API 嵌入）。

### 3.1 为什么契约是 Whippet IR 而不是 LLVM IR

讨论过"直接拿 LLVM IR 当接口"的方案，否决理由记录在此（也是给未来前端的选型说明）：

- **内存**：LLVM 内存表示每条指令 100+ B（Value + Use 链表），5k 行源文件对应约 2.5 万条 IR，驻留 10~20 MB，是源文件的 50~100 倍，直接击穿 §9.2 的 16× 预算；Whippet IR 用 u32 句柄 + 24 B 节点，同样规模约 1.2 MB；
- **编译速度**：§9.1 的预算下（每节点全流水线约 5000 次单位操作），胖表示的每一次指针解引用都是税；
- **正确性**：`nsw/nuw/exact` 标志与 `poison/undef/freeze` 语义是 LLVM 正确性 bug 的重灾区。Whippet IR 干脆没有这些概念——算术就是定长回绕，没有 flag，没有 poison，唯一 undefined 是内存错误。语义简单到不需要"复刻"，这是它比 LLVM IR 轻一个数量级的根本原因。

结论：想要 LLVM IR 生态的借用方（如 ETCC），请在前端自己完成 LLVM IR → Whippet IR 的 lowering（对 ETCC 而言工作量可控，因为它本来就生成 LLVM IR，相当于把 emit 后端换一套目标）。这个翻译层**不是 Whippet 的项目**，Whippet 不提供、不维护、不背书其正确性。

### 3.2 对前端产出的硬性要求（契约条款）

前端必须把以下工作做完再交给 Whippet，后端不做、也不检查：

1. **SSA 已构建**：phi 节点就位，mem2reg 已完成；Whippet 不做 SSA 重建；
2. **类型已降级**：只有 i8/i16/i32/i64/f32/f64/ptr 七种操作数类型，结构体/数组已展开为指针+偏移；
3. **控制流已展平**：显式基本块 + br/switch/ret，无结构化语句残留；
4. **语义已裁决**：任何源语言的 UB 或 poison 类语义在前端处理完毕，交给 Whippet 的每条指令都有确定行为；
5. **聚合返回值已处理**：多返回值用显式 out-ptr 参数传递（`extractvalue/insertvalue` 没有对应物）。

Whippet 侧唯一的"海关"动作：解析时遇到非法 opcode/类型/格式直接报错定位——拒绝畸形输入，但不理解任何前端语义。

## 4. Whippet IR 定义

### 4.1 形态

- 无限虚拟寄存器（%v0, %v1, ...），SSA 形式，phi 节点仅出现在基本块开头；
- 类型化操作数：i8 / i16 / i32 / i64 / f32 / f64 / ptr；
- 显式基本块 + 显式分支 / 条件分支 / 跳转表（switch），无结构化控制流；
- 函数级作用域，全局符号走符号表段。

### 4.2 文本形式样例

```javascript
func @add_mul(i32 %a, i32 %b) -> i32 {
entry:
  %v0 = mul i32 %a, 4
  %v1 = add i32 %v0, %b
  ret i32 %v1
}
```

### 4.3 关键设计决定

- 文本形式同时是**稳定的外部契约**（按本文件定义，语义版本化）与调试输出；round-trip 无损是对它的要求（M0 验收）；
- **跳转表是一等 IR 指令**（`switch %tag, [block0, ...], default`），不降级为比较链——否则指令选择无法从一串 `cmp+jcc` 里逆向出 `jmp [table+rax*8]`。这是为 Cavvy 模式匹配之类"按标签密集分派"的语义预留的；
- opcode 空间保留 128 个语言扩展槽，不认识的 opcode 报错而非跳过；
- 异常/协程扩展留待将来：异常要 landing pad 形态 + Windows unwinding 表支持，动的是寄存器分配的骨头；协程状态机 lowering 可表达，尾调用保证记给前端。

## 5. 中端：Pass 流水线

| # | Pass | 作用 | 档位 | 为什么在这个位置 |
| --- | --- | --- | --- | --- |
| 1 | 常量折叠/传播 | 把 `%v0 = add i32 2, 3` 变成 `5` | O1+ | 最便宜，越早做后面的 pass 看到的指令越少 |
| 2 | 空块消除 + 不可达块删除 | 简化控制流图 | O1+ | CFG 变简单后再算活跃性，bitvector 更短 |
| 3 | 复写传播 | `%v1 = copy %v0` 就地替换 | O1+ | 减少虚拟寄存器数量，直接给寄存器分配减压 |
| 4 | 死代码消除 | 删除无副作用且结果不用的指令 | O1+ | 指令越少，指令选择和发射越快 |
| 5 | GVN | 全局公共子表达式消除 | O2+ | 代价最高的一个，放在收益确定性最强的位置之后 |
| 6 | 简单强度削减 | `x*2^k → x<<k`，`x*3 → lea` 留给发射阶段模式匹配 | O1+ | 移交给发射阶段利用 x86 寻址模式 |

### 5.1 优化档位

| 档位 | 中端 | 指令选择 | 寄存器分配 | 用途 |
| --- | --- | --- | --- | --- |
| **-O0** | 无（直通） | naive | 线性扫描（仅保正确） | 调 bug、最快编译 |
| **-O1** | pass 1–4、6 | naive + 窥孔 | 线性扫描 | **默认档**，20k 行/秒指标对应此档 |
| **-O2** | pass 1–6 全量 | naive + 窥孔（更多模式） | 线性扫描 + spill 优化 | 发布构建 |
| **-O3** | O2 全部 | 更多窥孔模式 | 图着色（Chaitin） | 预留；O1/O2 稳定后再排期 |

每一遍都按"线性 + 小常数"的标准实现，遍历次数全函数 ≤ 2 轮（迭代到不动点只许出现在常量折叠+传播组合里，且限 3 次）。-O3 的图着色不受此约束。

## 6. 指令选择

不做复杂的树覆盖（BURG 那套表驱动对单人维护太贵），用**两遍简单方案**：

1. **逐指令翻译**：SSA 指令 → naive 机器码序列（正确优先，大量冗余 mov）；
2. **窥孔优化**（peephole）：局部窗口（默认 4 条指令）模式匹配，消除冗余 mov、合并寻址模式。

x86-64 专属模式举例（发射层的"白捡的性能"）：

- `add %x, %y` 且 %x 已被 copy 进结果寄存器 → 直接 `add dst, src`，省一条 mov；
- `mul %x, 2^k` → `shl`；`mul %x, 3/5/9` → `lea dst, [x + x*2]` 类寻址；
- 三元 `a + b*scale` → 单条 `lea`；
- 比较+分支 → `cmp` + `jcc`，不产生中间值；setcc 模式单独处理布尔表达式。

## 7. 寄存器分配：线性扫描（O0–O2 档）

### 7.1 算法

经典 Poletto–Sarkar 线性扫描：活跃区间按起点排序，扫描过程中维护当前活跃集合，寄存器不够用就溢出（spill）到栈槽，溢出选**覆盖范围最短且不再被使用**的区间。O2 档在此基础上加 spill 优化（重用死亡槽位、合并连续 spill）。

### 7.2 复杂度推导（为什么默认是它）

定义变量：

- $n$：单函数虚拟寄存器（活跃区间）数量；
- 线性扫描：排序 $O(n \log n)$ + 单遍扫描 $O(n \cdot k)$，$k$ 为同时活跃区间数，实际中 $k \ll n$，近似 $O(n \log n)$；
- Chaitin 图着色：建冲突图最坏 $O(n^2)$ 条边检查 + 着色循环。

代入具体数字。取一个"大函数" $n = 1000$ 个虚拟寄存器：

- 线性扫描：$n \log_2 n = 1000 \times 10 = 10^4$ 次比较量级；
- 图着色：$n^2 = 10^6$ 次边操作量级。

差了约 **100 倍**。再看 $n = 5000$ 的极端函数：线性扫描约 $5000 \times 12.3 \approx 6 \times 10^4$；图着色 $2.5 \times 10^7$。差距拉到约 **400 倍**。

结论：线性扫描在 $n=5000$ 时仍只要几万次操作（微秒级），完全贴合"编译快"的目标。图着色只在 -O3 出现。

### 7.3 物理寄存器账本（Windows x64 ABI）

- 参数寄存器：RCX、RDX、R8、R9（整型）+ XMM0–3（浮点）；调用方维护 32 字节 shadow space；
- 调用方保存：RAX、RCX、RDX、R8–R11、XMM0–5；
- 被调方保存：RBX、RSP、RBP、RSI、RDI、R12–R15、XMM6–15；
- 后端可自由支配的默认池：RAX、R10、R11 + 按需保存/恢复的被调方保存寄存器。

XMM6–15 是被调方保存这一条是 MSVC ABI 与 SysV 的重要差异，发射层 prologue/epilogue 必须照此生成，SysV 移植时整段账本换表即可（这是把 ABI 做成数据表而不是散落 if 的原因）。

## 8. 发射层

两阶段走：

- **M0–M2：文本汇编发射**。生成 **Intel 语法 GNU as** 汇编文本（`.intel_syntax noprefix`），Windows 下经 clang/llvm-mc 或 MinGW as 汇编、lld-link 链接。选它而不是 MASM 的理由：同一套发射代码将来在 Linux 上原样复用，MASM 语法是 Windows 独有且怪癖多（PROC/ENDP 结构、INVOKE 宏等）；过渡期用外部汇编器，正确性先行，把"二进制编码、重定位、COFF 写出"整块风险后置；
- **M3：内部汇编器 + COFF 直写**。x86-64 编码表有限（REX 前缀 + opcode + ModRM 三件套），单人可完成；省去进程启动与磁盘往返，编译速度目标主要靠这一刀兑现。

调试信息：v1 只发 CodeView 的 .debug$S 最小子集（文件名 + 行号），PDB 完整格式不碰；DWARF 留给 Linux 移植时平行实现，格式层独立成模块。

## 9. 全局数值推导

### 9.1 编译速度预算

变量：

- $v = 20{,}000$ 行/秒：目标编译速度（-O1 档）；
- 单个 50 行的函数（Whippet IR 节点数约为行数 10 倍，记 $m = 500$ 个节点）；
- 单次节点操作（构建/访问）记一次"单位操作"。

每行可用预算：$\frac{1}{v} = \frac{1}{20{,}000}$ s $= 50\ \mu s$。50 行函数总预算 $= 50 \times 50\ \mu s = 2.5$ ms，折合 500 个节点 → **每个节点全流水线（含 IR 构建 + 5 个 O1 pass + 指令选择 + 发射）只允许约 5000 次单位操作**。这解释了 §5 的"每遍 ≤ 2 轮"约束：5 遍 × 2 轮 = 10 次遍历，留给每遍的常数必须 ≤ 500 次操作/节点。IR 解析是单次遍历，包含在这 10 次之内。

### 9.2 内存预算推导

变量：源文件大小 $S$（取 5k 行 × 40 B/行 = 200 KiB 的典型单文件）。目标峰值 ≤ $16S = 3.2$ MiB。

分解：

- Whippet IR 文本流式缓冲（滑动窗口，不全文驻留）：≤ 64 KiB；
- Whippet IR 节点：$5000$ 行 × 10 节点 × 24 B/节点（紧凑结构体，句柄用 u32）≈ 1.2 MiB；
- 活跃性 bitvector：$5000$ 虚拟寄存器 × $50$ 基本块 × 1 bit ≈ 31 KiB；
- 区间、栈槽、发射缓冲：≤ 200 KiB；
- 合计 ≈ 1.5 MiB < 3.2 MiB，余量 53%。

由此得出一个实现约束：**句柄用 u32 索引而不是 64 位指针**——节点数组内引用差 4 字节，1.2 MiB 这一项直接减半，缓存行内节点数翻倍。此约束同时是 §3.1 不选 LLVM IR 的量化依据：同样 2.5 万条指令，LLVM 胖表示 10~20 MB（50~100×源文件），必然击穿本预算。

### 9.3 代码质量自限条款

与 gcc -O1 差 20% 的衡量基准建议：fib / 冒泡 / 矩阵乘（int 与 float 两版）+ 一个指针遍历链表，共 5 个小程序，取几何平均。超过阈值只许在指令选择/窥孔层找补，不许给中端加 pass（防范围蔓延）。

## 10. 里程碑

v1.0 的 C 子集边界（已定）：**整数（含 long long、char、_Bool）、浮点（float/double）、算术与位运算、if/while/for/do-while、break/continue、函数与递归、指针（含函数指针）、数组（多维）、struct/union、枚举、typedef、sizeof、三目与逗号表达式**。不属于 v1.0：位域、变长数组（VLA）、可变参数（va_arg）、内联汇编、setjmp/longjmp、复数、Atomics。

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| M0 | Whippet IR 文本解析 + 打印器 + 空发射 | round-trip 无损；非法 opcode/格式报错定位 |
| M1 | naive 指令选择 → GNU as 文本，整数子集 | `add_mul` 样例汇编 + 链接 + 运行正确 |
| M2 | 函数调用、栈帧、Windows x64 ABI 全量 | 跨函数递归 fib 正确 |
| M3 | 内部汇编器 + COFF 直写，O1 pass 全量 | §9.1 编译速度达标 |
| M4 | 浮点与 XMM、struct/union 布局、-O2 档（GVN、spill 优化） | §9.3 质量基准达标，标记 v1.0 |

## 11. 已决事项与遗留问题

已定（2026-11-08）：

1. Whippet 为独立项目，ETCC 只是后续借用方（ETCC 现用 LLVM）；
2. 优化四档：-O0 / -O1（默认）/ -O2 / -O3（预留）；
3. v1.0 C 子集按 §10 执行；
4. 发射文本用 Intel 语法 GNU as，不用 MASM；
5. **接入契约是 Whippet IR（文本 + 库 API）**；从 LLVM IR 或其他语言到 Whippet IR 的适配层由前端自行负责，不属于 Whippet；契约硬性要求见 §3.2（SSA 已建、类型已降级、控制流已展平、语义已裁决、聚合返回值已处理）；
6. **实现语言：C**（Rust  toolchain 重且拖慢迭代、C++ 大而易错均否决）。三条工程纪律对冲 C 的风险：①一律 arena 分配、禁函数内散 malloc；②ASan+UBSan 常驻 CI；③差分测试从 M1 起建（随机程序对比 gcc/clang 输出，miscompile 只能靠对比防住）；
7. **构建系统：CMake，生成器用 Ninja**（Makefile 方言在 Linux GNU Make / Windows NMake 间不兼容，CMake 一份 CMakeLists 两端通吃；Ninja 两端都有、增量快）。开发编译器统一 clang，MSVC 仅作借用方兼容性验证目标。

遗留：

- **仓库形态**：独立仓库（前端通过文本 IR 管道或库 API 接入）还是 monorepo？
- **嵌入形态**：库 API（进程内）与子进程管道（whippet cli 读 .wir 文件）两种消费方式都支持，还是先只做管道？文本 IR 的扩展名暂定 .wir。
